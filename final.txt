Molt — Final Product Brief, Showcase Plan, and Build Prompt
Product thesis
Molt: Teach once. Verify before trusting. Reuse without repeated inference.

Molt is a local-first, verified CSV automation tool for recurring cleanup and normalization work. A user describes the desired transformation in natural language. An open-weight model proposes a constrained JSON recipe. Molt validates and tests that recipe against explicit examples and deterministic rules. A human approves the recipe before it becomes active. Compatible future CSV files run through the verified recipe without another model call. If the input changes or a precondition fails, Molt blocks the run and proposes a repair for testing and human approval.
Original motive
People repeatedly clean the same types of CSV exports: orders, expenses, registrations, inventory, customers, and operational reports. Repeating the task manually wastes time; handwritten scripts become brittle; using an LLM every time adds latency, cost, inconsistency, and avoidable data exposure.

Molt's core idea is to use AI for planning, not for every repeated execution. AI translates intent into a recipe; ordinary code performs the transformation; tests and invariants provide evidence; a person approves changes.
What is in scope
Supported file type
- CSV input and CSV output only.
- UTF-8 input; document supported delimiter and encoding behavior.
- Preview a bounded sample and profile the complete file within configured size/row limits.
- Preserve the original file. Write output to a new file using a temporary file and atomic rename after successful completion.
Supported recipe operations
1. Trim whitespace.
2. Rename columns.
3. Normalize case (upper/lower/title, only where semantics are clear).
4. Map values using explicit mappings.
5. Parse dates using explicit formats or a user-confirmed format.
6. Parse decimals using explicit locale/decimal-separator settings where ambiguity exists.
7. Split columns using a specified delimiter and target columns.
8. Deduplicate rows using explicitly selected key columns or full-row comparison.
9. Filter rows using allowlisted operators and typed values.
10. Select/reorder columns.
11. Remove empty rows according to a documented definition.
12. Fill missing values using explicit constants or supported rules.
13. Validate values against declared constraints (required, allowed values, type, range, pattern where safely supported).
Every operation must have a typed schema, defined input requirements, defined output behavior, and explicit failure behavior. Do not pass arbitrary Python, JavaScript, shell commands, expressions, or executable code from the model to the runner.
Not in scope
- General-purpose AI agent or arbitrary code generator.
- Browser automation.
- Excel, PDF, SQL database, or API automation.
- Automatic discovery of every business rule.
- Silent auto-repair or auto-promotion of changed recipes.
- Multi-user enterprise workflow management.
- Mandatory Temporal, Mastra, MongoDB Atlas, Tiger Data, or additional orchestration/database services in the MVP.
Core user journey
1. Create automation: user uploads a CSV and describes the transformation in natural language.
2. Profile input: Molt presents columns, inferred types, null rates, examples with sensitive values masked where configured, duplicate counts, and basic statistics. The sample should be bounded; do not send an entire file to the model.
3. Generate recipe: local Gemma via Ollama proposes a JSON recipe using only supported operations. The model also identifies assumptions and ambiguities.
4. Validate recipe structure: validate with a strict schema, operation allowlist, column references, type compatibility, and resource limits. Reject unknown operations or malformed fields.
5. Test and preview: run the recipe in a deterministic sandbox against a small preview and a test suite containing user-supplied expected examples, edge cases, and invariants. Show before/after output and a clear test report.
6. Resolve ambiguity: if date formats, decimal conventions, duplicate keys, missing-value policy, or mapping semantics are ambiguous, ask the user or leave the recipe blocked. Do not guess silently.
7. Approve version: user explicitly approves the tested recipe version. Record version, recipe hash, approval timestamp, and test report.
8. Reuse: compatible future CSV files are processed by the active recipe with zero LLM calls. Show the LLM call count for the run.
9. Detect drift: compare incoming headers, required columns, configured types, profile ranges, and operation preconditions with the recipe's requirements. If incompatible, stop execution, preserve the input, and place the run in a review/quarantine state.
10. Propose repair: Gemma may propose a new recipe version. Run the complete regression suite and new-input checks. Never make it active until a human approves it.
11. Audit and savings: record execution status, recipe version/hash, rows processed, test result, model calls, durations, warnings, and whether human intervention was required.
Recipe format
Use a versioned JSON document with a strict schema. Example shape:
{
  "recipe_version": 1,
  "name": "Normalize monthly orders export",
  "description": "Trim values, standardize status, parse dates, and select output columns.",
  "input_contract": {
    "required_columns": ["Order ID", " Status ", "Order Date"],
    "date_formats": {"Order Date": "%Y-%m-%d"},
    "decimal_conventions": {},
    "allow_extra_columns": true
  },
  "operations": [
    {"op": "trim_whitespace", "columns": [" Status "]},
    {"op": "rename_columns", "mapping": {"Order ID": "order_id", " Status ": "status", "Order Date": "order_date"}},
    {"op": "normalize_case", "columns": ["status"], "mode": "lower"},
    {"op": "parse_dates", "columns": ["order_date"], "formats": {"order_date": "%Y-%m-%d"}},
    {"op": "select_columns", "columns": ["order_id", "status", "order_date"]}
  ],
  "postconditions": [
    {"type": "required_columns", "columns": ["order_id", "status", "order_date"]},
    {"type": "no_new_nulls", "columns": ["order_id"]}
  ]
}
This is only an illustrative schema. The implementation must define every operation's exact arguments and behavior. Do not let the model define executable conditions outside the allowlisted schema. If the recipe schema or operation signatures change, increment the recipe version and test compatibility.
Verification and drift rules
Verification before approval
- Strict recipe schema validation.
- Verify that referenced columns exist at the relevant point in the operation sequence.
- Validate compatible operation order and parameter types.
- Run deterministic fixtures with known expected outputs.
- Check declared postconditions/invariants.
- Include edge cases: empty file, header-only file, missing column, empty string, whitespace-only value, malformed date, invalid decimal, duplicate key, delimiter edge case, unexpected value, and mixed casing.
- Compare actual output with expected output for each fixture.
- Keep regression fixtures for every approved change.
- Test idempotence only for operations or recipes explicitly declared idempotent; do not assume every operation can be safely applied twice.
- Provide a clear report containing pass/fail, the failing row/column or anonymized location, and the reason.
Drift detection
Molt should detect only declared and measurable forms of drift, such as:
- required columns missing or renamed;
- unexpected column/type changes where the input contract says they matter;
- configured value formats becoming invalid;
- operation preconditions failing;
- postconditions failing;
- data profiles crossing user-defined limits.
Do not claim to detect every semantic change. A drifted file must not silently produce a successful final output. It can be quarantined or receive an explicitly marked diagnostic preview, but the app must clearly distinguish that preview from approved output.
Ground truth
Include example CSV files and hand-authored expected output fixtures in the repository. Demo orders and expense exports are illustrative fixtures, not hard-coded product types. The product should work on any CSV that can be expressed with its supported operations.
Architecture decisions
- Frontend: React + TypeScript + Vite. Keep the UI simple and legible; no unnecessary animation or complex dashboard framework.
- Backend: Python + FastAPI.
- CSV engine: Python standard library csv plus typed transformation functions. Prefer transparent deterministic functions over opaque dataframe magic for the core runner.
- Recipe schema: Pydantic models or an equally strict validated schema.
- Local AI: Ollama with a configurable Gemma model name and base URL. Handle model unavailable, timeout, invalid JSON, and response truncation gracefully.
- Persistence: SQLite for recipes, versions, approvals, fixture references, runs, drift incidents, and metrics.
- Tests: pytest for operation unit tests, schema tests, integration tests, regression fixtures, and API tests.
- Observability: Sentry SDK/Agent Tracing for non-sensitive spans where configured. Keep telemetry useful without recording raw CSV rows, full prompts containing sensitive data, or secrets.
- Optional anomaly module: a separate TabPFN adapter behind a feature flag. It may return advisory anomaly signals only when the model and dependency are available and the selected data is suitable. It must not block deterministic validation or modify rows. If it is unavailable, core Molt must keep working.
Do not introduce a second database or workflow orchestrator for the sake of sponsor count. SQLite is sufficient for the local MVP. Do not add Mastra if it merely duplicates the explicit, testable workflow. Do not add Temporal unless there is a real durable, interruptible multi-step workflow need that the simple service cannot meet.

API surface
Use typed request/response models and meaningful error status codes. Exact route names can vary, but implement equivalent functionality for:
- GET /health — service health and model availability, without exposing secrets.
- POST /api/files/profile — profile an uploaded CSV safely.
- POST /api/recipes/propose — send a bounded profile and user instruction to Gemma and return a candidate recipe plus assumptions.
- POST /api/recipes/validate — validate structure, allowlisted operations, column references, and preconditions.
- POST /api/recipes/test — run fixtures and a preview; return a structured verification report.
- POST /api/recipes/{id}/approve — approve an exact recipe version/hash only after required tests pass.
- GET /api/recipes and GET /api/recipes/{id} — list and inspect recipes and versions.
- POST /api/automations/{id}/run — execute an approved recipe against a new CSV if it satisfies its input contract.
- GET /api/runs and GET /api/runs/{id} — execution history and details.
- POST /api/automations/{id}/repair-proposal — propose a new version after drift; must not promote it automatically.
- POST /api/repair-proposals/{id}/approve — promote the specific repaired version only after all required checks pass and an authorized user approves it.
Never trust a client-supplied recipe ID, path, or approval flag without server-side verification. Avoid arbitrary filesystem paths from the client; use generated server-side file IDs and a configured working directory.
UI screens
1. Home / Automations: list recipe name, status, latest run, recipe version, and model calls avoided.
2. New automation: upload CSV, enter task in natural language, inspect profile, generate recipe.
3. Recipe review: readable transformation steps, explicit assumptions, warnings, editable parameters only within the schema, and a before/after preview.
4. Verification report: test fixture results, postconditions, counts, warnings, and blocked reasons.
5. Approval: clearly show the exact recipe version/hash being approved.
6. Run results: output download, rows read/written/rejected, warnings, status, recipe version, and whether an LLM was called.
7. Drift / repair review: show the failed precondition, proposed differences, regression results, and explicit approve/reject controls.
8. Run ledger: execution history, actual LLM call count, elapsed time, failures, and transparent estimates of calls/time/cost avoided. Label any estimated value as an estimate and state the baseline assumption.
9. Settings / integrations: Ollama status and model selection; optional Sentry configuration; optional TabPFN availability. Do not show secrets after saving.
Every screen needs loading, empty, error, and disabled states. Do not render fake success states when a model or integration is unavailable.
Safety and privacy requirements
- Source files are immutable; output is written separately.
- Enforce file size, row count, and processing time limits.
- Avoid loading unbounded files fully into memory when a streaming implementation is practical.
- Reject dangerous or unknown recipe operations.
- Never execute model-generated code or shell commands.
- Validate paths and use a dedicated working directory; prevent path traversal.
- Escape CSV fields correctly on output.
- Treat CSV content as untrusted data, not as instructions to the model. Ignore prompt-injection-like instructions appearing inside a cell.
- Send the model only the minimum profile/sample required; make masking configurable and document limitations.
- Do not log full rows, sensitive samples, API keys, model secrets, or full raw uploads.
- For ambiguous dates/decimals/business rules, ask the user or block the recipe instead of guessing.
- A failed validation, failed postcondition, or unexpected schema change must not create a green “success” run.
- Repair proposals never auto-promote. Human approval is mandatory.
- The UI must explain what is local, what leaves the machine, and what an optional telemetry integration collects.

Evaluation plan and metrics
Build a repeatable benchmark with fixed CSV inputs, user tasks, expected outputs, and drifted inputs. Compare:
- Baseline A: use an LLM for every file/run.
- Baseline B: a fixed manual script for the known sample only.
- Molt: compile one recipe, test and approve it, then reuse it on compatible inputs and block drift.
Measure and report actual results:
- LLM calls per N compatible runs.
- Number and percentage of fixtures that pass expected-output comparison.
- Unsafe/invalid recipes blocked before execution.
- Drifted files correctly blocked in the test suite.
- Repair proposals that pass regression tests (not just generated proposals).
- Failed runs and false-positive drift warnings on the benchmark.
- Execution time and model latency where captured.
- Human approvals required and total user steps for initial setup vs reuse.
- Estimated tokens or cost only when actual token data or a disclosed calculation method exists; label estimates clearly.
Never claim guaranteed correctness. Report the exact fixture set and sample size. Do not advertise “zero silent errors” unless the benchmark and definition make that statement demonstrably true.

Definition of done
The MVP is ready to showcase only when all applicable items below work end-to-end:
- A natural-language request can produce a valid recipe from a configured local Gemma model.
- Unsupported instructions, ambiguous formats, invalid recipe JSON, and unknown operations are rejected or routed to clarification.
- Supported transformations run deterministically against CSVs and produce expected outputs.
- Recipe verification report is based on actual tests, not mocked results.
- User must explicitly approve a passing recipe version.
- A compatible subsequent input runs without a model call, and that fact is recorded.
- An incompatible/drifted input is blocked/quarantined and cannot become a successful approved output.
- A repair is a new version that must pass the complete regression suite and human approval before use.
- Source file remains unchanged; no arbitrary generated code is executed.
- Run history and truthful savings metrics persist across restarts.
- Automated tests cover operations, recipe validation, drift, approvals, errors, and API behavior.
- README setup instructions work from a clean checkout, including model installation/configuration and limitations.
- Optional sponsors are either genuinely integrated and documented or removed from claims.
